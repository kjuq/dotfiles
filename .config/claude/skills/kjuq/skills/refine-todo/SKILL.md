# `/refine-todo`: TODO の詳細を詰める

`/create-todo` で積んだ TODO の blueprint から曖昧さを取り除き、`/start-todo` ですぐ実装に取り掛かれる状態にする。`/create-todo` は 1 shot で積むことを優先し、与えられた情報以上のことを書かないため、blueprint は概要だけだったり「未定」の節を含んだりする。その詳細を、ユーザーに確認を取りながら詰めるのがこのスキルの役割である。

このスキルでは blueprint の更新だけを行い、実装には着手しない。blueprint 以外のファイルは編集しない。

指定:

$ARGUMENTS

## 1. パスを決める

- Project root は `git rev-parse --show-toplevel` で求める。git リポジトリでなければカレントディレクトリを Project root とする。
- blueprint ディレクトリは `<project-root>/_kjuq/blueprint/`、TODO 一覧は `<project-root>/_kjuq/TODO.md`。
- どちらも存在しなければ、TODO がまだ無いことを伝えて終了する。

## 2. TODO を特定する

指定の形に応じて対象を決める。

- 数字のとき: `<project-root>/_kjuq/blueprint/<num>-*.md` に一致するファイルを対象にする。見つからなければその旨と TODO.md の一覧を示して終了する。
- 自然言語のとき: TODO.md の各行のサマリーと、必要なら blueprint の中身を読み、指示に最も合う TODO を選ぶ。
	- 一つに絞り込めれば、どの TODO (番号とサマリー) を詰めるかを一行伝えてから進める。
	- 候補が複数あって決めきれない場合や、該当するものが無い場合は、候補を示してユーザーに選んでもらう。
- 空のとき: TODO.md の一覧を示し、どれを詰めるかをユーザーに選んでもらう。

## 3. 現状を調べる

- blueprint を読み、背景・やりたいこと・完了条件・メモを把握する。
- メモにある関連ファイルや URL に目を通す。
- 関連するコードや設定、ドキュメントを読み、現状を把握する。blueprint 作成時から状況が変わっている可能性もあるので、記述と現状が食い違っていないかも確認する。
- すでに完了している、または前提が崩れていて不要になっていると分かった場合は、その旨を伝えて blueprint をどうするかユーザーに確認する。

## 4. 曖昧な点を洗い出す

blueprint を、別のセッションが会話の文脈なしに読んで、質問せずに実装を始められるかという観点で点検する。特に次を確認する。

- スコープ: 何をやり、何をやらないか。
- 方針: 実装のアプローチ。複数の案があるなら、どれを採るか。
- 変更対象: 作成・変更・削除するファイルや設定、その中のどの部分か。
- 仕様の細部: 命名、インターフェース、入出力の形式、エッジケースやエラー時の挙動。
- 依存と前提: 必要なツールやパッケージ、先に済ませておくべき作業。
- 完了条件: 達成したかを客観的に判定できるか。どう確かめるか (実行するコマンド、テスト、目視で確認する箇所など)。
- 「未定」の節: すべて埋まるか。

## 5. 曖昧な点を解消する

曖昧な点は、自分の判断だけで確定させず、ユーザーに確認を取って決める。

- 調べれば分かる現状の事実 (既存ファイルの場所、使われているライブラリ、既存の命名規則など) は、ユーザーに聞かずに調べて書く。
- 方針、スコープ、仕様、完了条件など、判断を伴うものはユーザーに確認する。コードや慣習から妥当な案が一つに定まりそうな場合も、推奨案として示して確認を取る。
- AskUserQuestion を使い、選択肢と推奨案、それぞれの影響を示して聞く。
- 質問はなるべくまとめて一度に聞く。回答を受けて新たな論点が出たら、それも確認する。
- 決まった内容と根拠は blueprint の「決定事項」に残す。

## 6. blueprint を書き直す

対象の blueprint を、次のテンプレートに沿って上書きする。ファイル名と番号は変えない。本文は日本語で書く。

- 元の内容 (特に背景や作成日) は失わないように引き継ぐ。
- 会話の文脈に頼らず、このファイルだけで実装に取り掛かれる自己完結した内容にする。
- 手順は、そのまま上から実行していけば完了条件に到達できる粒度で書く。コードの全文を書く必要はないが、変更箇所と変更内容が一意に分かるようにする。

テンプレート:

```markdown
# <タイトル (日本語)>

作成日: YYYY-MM-DD
精緻化日: YYYY-MM-DD

## 背景

なぜやりたいのか。きっかけや現状の問題。

## やりたいこと

何をするのか。スコープを具体的に。

## やらないこと

スコープ外とするもの。なければ節ごと省略する。

## 方針

採用する実装のアプローチと、その理由。

## 変更対象

作成・変更・削除するファイルや設定の一覧と、それぞれで何をするか。

## 手順

1. 実装の手順を順番に。

## 完了条件

- 達成を客観的に判定できる条件と、その確かめ方。

## 決定事項

詰める過程で決めたことと、その根拠 (ユーザーの回答、調べて分かった事実など)。

## メモ

関連するファイルのパス、参考 URL、実装時の注意点など。なければ節ごと省略する。
```

再度 `/refine-todo` を実行した場合は、精緻化日を更新し、既存の決定事項に追記する形で書き直す。

## 7. TODO.md を確認する

詰めた結果、TODO.md のサマリーが内容と合わなくなった場合に限り、該当する一行のサマリー部分だけを更新する。リンクや他の行は変更しない。

## 8. 報告する

- 更新した blueprint のパスを伝える。
- 決まった主な事項を簡潔にまとめる。
- 着手するときは `/start-todo <num>` を使えることを添える。
